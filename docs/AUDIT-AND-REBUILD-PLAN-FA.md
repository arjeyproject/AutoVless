# گزارش ممیزی و نقشهٔ بازسازی AutoVless

تاریخ ممیزی: 2026-11-06
مخزن بررسی‌شده: `arjeyproject/AutoVless`

## جمع‌بندی اجرایی

AutoVless در وضعیت فعلی یک ربات Telegram نسبتاً کامل با API مینی‌اپ، احراز هویت مبتنی بر `Telegram WebApp initData`، دیتابیس SQLite، ساخت کانفیگ‌های VLESS/Trojan/WARP، پنل ادمین، لاگ رویداد، سهمیهٔ دعوت/پرداخت و اسکنر endpoint است. بنابراین بازسازی کامل از صفر پرریسک و غیرضروری است؛ پیشنهاد می‌شود روی همین پایه یک نسخهٔ سخت‌سازی‌شده و قابل‌ممیزی ساخته شود.

این پروژه فقط باید برای سرورها، دامنه‌ها و حساب‌هایی استفاده شود که مالکیت یا مجوز صریح آن‌ها در اختیار اپراتور سامانه است. قابلیت اسکن گستردهٔ IPهای عمومی، انتخاب IP بر اساس اپراتور برای دورزدن فیلترینگ، و تولید تونل‌های ناشناس‌سازی خارج از زیرساخت مجاز، در نسخهٔ پیشنهادی فعال نخواهد بود.

## قابلیت‌هایی که همین حالا وجود دارند

- ربات Telegram با aiogram و منوی دو زبانهٔ فارسی/انگلیسی.
- مینی‌اپ استاتیک در `webapp/` و API در `bot/api.py`.
- اعتبارسنجی HMAC دادهٔ امضاشدهٔ Telegram در هر endpoint محافظت‌شده.
- کنترل ادمین بر پایهٔ شناسهٔ عددی Telegram.
- جداول کاربران، پنل‌ها، endpointها، رویدادها، تیکت‌ها، WARP و تنظیمات.
- ذخیرهٔ رمزنگاری‌شدهٔ tokenهای پنل با Fernet مشتق‌شده از `SECRET_KEY`.
- ساخت و بازسازی پنل، لینک اشتراک، QR و فایل‌های خروجی.
- اسکن و health-check برای endpointها، curator و autopilot.
- پنل مدیریت، قفل دعوت، بخش رایگان و مسیر پرداخت.

## یافته‌های مهم و ریسک‌ها

### 1. دامنهٔ اسکن بیش از حد وسیع است

`bot/scanner_v2.py` رنج‌های عمومی Cloudflare را به‌صورت subnet sweep پیمایش می‌کند و `.env.example` نیز مقادیر concurrency و batch بالا دارد. این رفتار از نظر عملیاتی پرهزینه، از نظر حقوقی/سیاستی پرریسک، و برای یک سرویس عمومی قابل سوءاستفاده است.

**تصمیم بازسازی:** اسکن عمومی و انتخاب IP بر اساس اپراتور حذف/غیرفعال شود. به‌جای آن فقط این منابع مجاز باقی بمانند:

- endpointهای ثبت‌شده توسط ادمین؛
- دامنه‌ها و IPهای تحت مالکیت/مجوز که در allowlist ثبت شده‌اند؛
- health-check محدود و rate-limited روی همان allowlist.

### 2. حساب کاربری نیازمند مدل روشن‌تر است

کاربر فعلاً با `tg_id` شناخته می‌شود و جدول `panels` برای هر کاربر یک رکورد اصلی دارد. برای مشاهدهٔ امن اطلاعات، لازم است مفهوم نشست، دستگاه، تاریخچهٔ کانفیگ و وضعیت revoke جداگانه مدل شود.

**کارهای لازم:**

- افزودن `user_sessions` با نشست کوتاه‌عمر و revoke؛
- افزودن `config_issuances` با شناسه، نوع، زمان صدور، انقضا، وضعیت revoke و fingerprint؛
- عدم نمایش token خام پنل در API؛
- ثبت رویدادهای login، issuance، download، revoke و admin action.

### 3. کنترل دسترسی و ضدسوءاستفاده باید متمرکز شود

`guarded` احراز هویت و قفل دعوت/پرداخت را انجام می‌دهد، اما rate limit، idempotency، CSRF/origin policy و کنترل هم‌زمانی باید در یک لایهٔ مستقل و قابل تست قرار گیرد.

**کارهای لازم:**

- rate limit جدا برای state، build، rescan، download و admin؛
- محدودیت تعداد کانفیگ فعال برای هر کاربر؛
- revoke فوری و rotation برای لینک‌های حساس؛
- بررسی `Origin`/`Host` مجاز برای درخواست‌های مرورگری؛
- پاسخ خطای عمومی به کاربر و ثبت جزئیات فقط در لاگ امن.

### 4. TTL دادهٔ Telegram باید با زمان آینده نیز مقابله کند

در `verify_init_data` انقضای داده بررسی می‌شود، اما داده‌ای که `auth_date` آن در آینده باشد باید نیز رد شود. TTL پیش‌فرض ۲۴ ساعت برای نشست‌های حساس زیاد است.

**کارهای لازم:**

- رد `auth_date` آینده با clock skew کوچک؛
- کاهش TTL برای عملیات حساس؛
- تبدیل initData معتبر به session cookie/httpOnly کوتاه‌عمر در صورت نیاز؛
- افزودن تست‌های replay و clock skew.

### 5. خروجی‌های شبکه‌ای باید محدود و قابل ممیزی شوند

پشتیبانی از HTTP Upgrade، XHTTP یا هر transport دیگر فقط وقتی مجاز است که endpoint و دامنه تحت مالکیت اپراتور سامانه باشد و در allowlist ثبت شده باشد. این قابلیت‌ها نباید برای اسکن عمومی یا پنهان‌سازی ترافیک اشخاص ثالث ارائه شوند.

**تصمیم بازسازی:** transport به‌صورت plugin محدود پیاده‌سازی شود؛ هر plugin باید مالکیت/allowlist، health-check، محدودیت نرخ و قابلیت revoke داشته باشد. transportهای بدون تست و بدون مستندات حذف شوند.

### 6. اسرار و دادهٔ حساس

- `SECRET_KEY` به‌صورت فایل محلی fallback تولید می‌شود؛ برای production باید Secret Manager یا secret محیطی اجباری شود.
- `STORE_TOKENS=true` باید opt-in باشد و با rotation/revoke همراه شود.
- لاگ‌ها نباید token، UUID کامل، private key یا لینک اشتراک کامل را چاپ کنند.
- backup دیتابیس و retention لاگ باید مستند و قابل تنظیم باشد.

## مواردی که باید حذف یا خاموش شوند

1. اسکن کامل رنج‌های عمومی Cloudflare و جدول‌بندی IP برای هر اپراتور.
2. منابع seed ناشناس یا third-party که مالکیتشان روشن نیست.
3. proxy relayهای عمومی ناشناس به‌عنوان مسیر پیش‌فرض.
4. export خودکار کانفیگ برای endpointی که در allowlist و مالکیت سامانه نیست.
5. هر گزینه‌ای که ادعای «IP تمیز قطعی» یا تضمین عبور از محدودیت شبکه بدهد.
6. logging لینک‌ها، tokenها، private keyها و دادهٔ خام Telegram.
7. transportهای experimental که health-check و تست سازگاری ندارند.

## قابلیت‌های لازم برای نسخهٔ بازسازی‌شده

### حساب کاربری

- ورود با Telegram Mini App و نمایش نام/شناسهٔ محدودشده.
- فهرست کانفیگ‌های کاربر با نوع، تاریخ صدور، انقضا و وضعیت.
- دانلود/کپی/QR با لینک کوتاه‌عمر.
- revoke دستی و صدور دوباره.
- نمایش سهمیه، تعداد دستگاه‌ها و زمان آخرین فعالیت.

### پنل ادمین

- مدیریت کاربران، ban/unban، سهمیه و revoke.
- allowlist دامنه/IP با توضیح مالکیت، صاحب سرویس و زمان تأیید.
- health-check محدود، قابل زمان‌بندی و rate-limited.
- audit log فیلترپذیر و export بدون اسرار.
- مشاهدهٔ خطاها، queue jobها و وضعیت workerها.

### مینی‌اپ

- طراحی RTL واقعی برای فارسی و LTR برای فیلدهای فنی.
- داشبورد کارت‌محور با وضعیت سرویس، کانفیگ‌ها، سهمیه و اعلان‌ها.
- wizard ساخت کانفیگ با نمایش واضح مالکیت endpoint و زمان انقضا.
- empty state، loading state، خطای قابل فهم و تأیید عملیات مخرب.
- dark/light theme، دسترس‌پذیری، responsive layout و کاهش دادهٔ ارسالی.

### زیرساخت و کیفیت

- migrationهای نسخه‌دار به‌جای migration صرفاً best-effort.
- تست unit برای auth، ACL، token handling و config issuance.
- تست integration برای API و Telegram initData.
- health/readiness endpoint جدا.
- backup و restore مستند، retention و پاک‌سازی اطلاعات قدیمی.
- Docker hardening، اجرای non-root و محدودسازی شبکهٔ خروجی worker.

## نقشهٔ اجرای پیشنهادی

### فاز 1 — خط پایه و ایمن‌سازی فوری

- freeze کردن اسکن عمومی و relayهای ناشناس در production؛
- افزودن تست‌های auth و جلوگیری از auth_date آینده؛
- redact کردن secretها در log؛
- افزودن rate limit و سقف jobهای هم‌زمان؛
- ایجاد migration framework و backup check.

### فاز 2 — مدل حساب و صدور کانفیگ

- جداول session، issuance، device و audit؛
- APIهای list/detail/revoke/download؛
- لینک‌های کوتاه‌عمر و عدم بازگرداندن secret خام در state؛
- job queue idempotent برای build/rebuild.

### فاز 3 — بازطراحی مینی‌اپ

- تفکیک لایهٔ state، API client و UI components؛
- صفحه‌های Dashboard، My Configs، Create، Activity، Support و Admin؛
- RTL/LTR، theme، accessibility و error boundary؛
- route manifest و بررسی build/diagnostics.

### فاز 4 — transportهای مجاز

- تعریف interface برای transport؛
- فعال‌سازی فقط برای allowlist مالکیتی؛
- health-check اختصاصی و تست سازگاری؛
- revoke و گزارش سلامت برای هر transport.

### فاز 5 — استقرار و ممیزی نهایی

- اجرای تست‌ها و lint/type checks؛
- بررسی Docker و secret policy؛
- مستندسازی نصب، backup، rollback و incident response؛
- ساخت release candidate و گزارش تغییرات.

## نتیجهٔ فعلی

هستهٔ محصول موجود است و ارزش نگهداری دارد. بیشترین کمبود فعلی در «کنترل دامنه و مالکیت endpointها»، «مدل صدور و لغو کانفیگ»، «rate limit و audit»، و «امنیت operational» است؛ نه در اضافه‌کردن پروتکل‌های بیشتر. نسخهٔ جدید باید قابلیت‌های پرریسک اسکن عمومی و relay ناشناس را حذف کند و تجربهٔ کاربری و مدیریت حساب را به‌طور محسوسی بهتر کند.
